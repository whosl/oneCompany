# Level 03 三级考题说明：复杂需求到可验证工程项目的多智能体交付系统

> 关键词：多智能体、工程交付、delivery_app、测试验证、部署材料、交付报告  
> 满分 100 分，建议通过线 75 分。

---

## 1. 题目定位

**题目名称：** 复杂需求到可验证工程项目的多智能体交付系统  
**题目类型：** 独立项目题目

学员需要开发一个**多智能体工程交付系统**。用户输入复杂业务需求后，系统需要完成：

- 计划生成
- 架构设计
- 代码生成
- 测试执行
- 自我评审
- 缺陷修复
- 部署说明
- 最终输出可运行、可测试、可部署的工程项目

**核心重点：**  
不是直接手写一个固定的 AI 销售线索管理助手，而是实现一个可以根据输入需求自动生成或维护 `delivery_app` 的多智能体交付系统。

---

## 2. 题目背景

真实研发中，需求从想法变成可交付工程项目，需要经历：

1. 需求理解
2. 计划拆解
3. 架构设计
4. 代码实现
5. 测试验证
6. 质量评审
7. 交付部署

本题要求学员开发一个具备多角色协作能力的交付型智能体系统，能够自主推进完整工程交付闭环。

---

## 3. 使用对象

| 使用对象 | 关注点 |
|---|---|
| 业务用户 | 输入复杂需求，并验证交付工程是否能完成核心流程 |
| 工程负责人 | 审查架构、任务拆解、测试、部署方式和剩余风险 |
| 评分人员 | 验证智能体是否具备多角色协作、工具调用、测试执行、自检修复和交付能力 |

---

## 4. 统一测试输入示例

下面这段文字是评分人员运行你开发的多智能体交付系统时输入的测试需求，**不是要求你直接手写一个固定应用**。

```text
设计并实现一个 AI 销售线索管理助手。销售人员可以导入客户线索，系统自动判断客户意向等级，生成跟进建议，记录跟进历史。普通销售只能查看自己的客户，销售主管可以查看团队客户数据。系统需要支持客户列表、线索评分、跟进记录、权限控制和数据统计。
```

**提交重点：**  
你的多智能体交付系统本身能否根据这段输入，自动生成或维护 `delivery_app`，并完成测试验证和交付报告。

---

## 5. 用户运行和使用交付工程的流程

| 步骤 | 名称 | 说明 |
|---:|---|---|
| 1 | 输入业务目标 | 用户输入业务需求、目标用户、期望技术栈或默认约束 |
| 2 | 确认计划 | 智能体生成交付计划、范围边界、风险和任务拆解 |
| 3 | 自动实现 | 系统生成 `delivery_app` 工程代码、数据模型、页面、接口或本地服务 |
| 4 | 测试自检 | 智能体运行测试或验证脚本，根据失败结果进行修复 |
| 5 | 运行验收 | 用户启动 `delivery_app`，以不同角色登录或切换身份，完成核心业务流程 |
| 6 | 交付报告 | 系统输出已实现内容、验证结果、已知限制和后续迭代建议 |

## 6. 学员需要实现的系统功能

| 功能 | 要求 |
|---|---|
| 任务入口 | 用户输入复杂业务需求，系统创建一次工程交付任务 |
| 计划面板 | 展示需求梳理、架构方案、任务拆解、优先级和风险 |
| 代码生成与文件管理 | 生成可运行工程项目所需文件，并记录修改历史 |
| 测试与验证 | 生成并执行测试脚本或验证步骤，展示测试结果 |
| 自我评审 | 对功能完整性、权限边界、数据状态、运行路径进行检查 |
| 交付中心 | 提供运行说明、账号说明、验收用例和最终报告 |

## 7. Agent 架构要求

系统至少需要满足：

1. 至少包含 **4 个角色或子 Agent**，例如 Planner、Architect、Builder、Tester、Reviewer、Reporter。
2. 至少封装 **8 个工具能力**，例如文件读写、代码生成、依赖安装、测试执行、数据初始化、权限检查、报告生成、部署配置生成。
3. 至少接入 **2 个 MCP 或等价工具服务**，例如文件系统、数据库、代码执行、测试运行、网页检索或容器构建服务。
4. 交付工程的生成或维护过程必须由多智能体系统完成，不能预先手写固定业务应用后只做包装。
5. 必须包含测试执行工具，能够运行测试脚本或验证脚本并保存结果。
6. 必须包含评审或自检阶段，能够输出问题清单、修复记录或剩余风险。
7. 必须生成 `delivery_app` 目录，并提供 Dockerfile、`docker-compose.yml` 或等价一键启动脚本。

> 上述角色可以是真正的多智能体，也可以是一个智能体内部的多阶段状态机，但职责边界、输入输出和调用日志必须清楚。

## 8. 三级交付标准

三级的关键不是页面更多，而是**工程闭环更完整**。

评分人员需要能够：

- 运行 `delivery_app`
- 切换不同角色
- 看到数据状态变化
- 执行测试或验收脚本
- 阅读智能体的自检、修复记录和交付报告

### 8.1 工程完整性最低要求

- 有可运行应用，不只是静态页面。
- 有数据存储，可以是 LocalStorage、JSON 文件、SQLite 或数据库。
- 有角色差异，至少包含普通销售和销售主管两类视角。
- 有核心业务对象：客户线索、跟进记录、评分结果、建议内容。
- 有测试或验证脚本，能证明关键流程可用。
- 有 Dockerfile、`docker-compose.yml` 或等价一键启动脚本。

### 8.2 验证完整性最低要求

- 新用户能根据运行说明启动系统并进入测试账号。
- 普通销售只能看到自己的客户线索，主管能看到团队数据。
- 用户新增线索后，系统能产生评分和跟进建议。
- 用户新增跟进记录后，列表、详情或统计中能看到变化。
- 异常状态有提示，例如空列表、缺少字段、无权限访问。

## 9. AI 销售线索管理助手交付工程最低路径

评分时会重点检查 `delivery_app` 是否至少完成以下路径：

1. 以销售身份进入系统，导入或新增客户线索。
2. 系统根据行业、规模、预算、需求描述等字段生成意向等级。
3. 系统给出下一步跟进建议，并说明判断依据。
4. 销售添加一次跟进记录，状态在客户详情中更新。
5. 切换为销售主管，查看团队客户列表和统计摘要。
6. 尝试访问非授权数据，系统应限制或给出清晰提示。

## 14. 提交后的评分流程

### 第一步：材料预检

- 检查压缩包命名、目录结构和必交文件。
- 检查是否包含中间编译文件、构建产物或敏感信息。
- 检查 README、环境变量示例、日志和输出样例是否完整。

### 第二步：AI 评测

- 按 README 执行安装、启动和测试命令。
- 使用统一示例需求检查生成结果和运行日志。
- 依据评分表生成初步评分和问题清单。

### 第三步：人工复核

- 复核 AI 评测中的关键扣分项和争议项。
- 检查 Agent 阶段、结构化输出、测试证据和交付报告。
- 对照评分表确认最终分数和是否通过。

## 15. 三级题目的核心判断

三级考察的问题是：

> 能否让多智能体系统完成一个可验证工程项目的交付闭环？

合格提交应体现：

> 多智能体交付系统 + `delivery_app` + 测试验证 + 部署材料 + 交付报告。

不合格的典型情况是：

> 只有页面样例，没有数据、权限、测试或自检。
